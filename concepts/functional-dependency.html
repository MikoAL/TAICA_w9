functional dependency（函數相依）

動機

一個外送平台把訂單存成一個 relation，為了方便，每一列都順手存了店家電話。

orders(order_no, shop, shop_phone, item)
order_noshopshop_phoneitem
t₁A001阿嬤豆花02-5550-0199花生豆花
t₂A002小林麵館02-5550-0202牛肉麵
t₃A003阿嬤豆花02-5550-0101芋圓豆花

阿嬤豆花換了電話，工讀生只改到 t₁。現在 t₁ 和 t₃ 兩列對同一間店給出兩個不同的電話，沒人知道哪個是對的。

現實裡有一條規則：「同一間店只有一個電話」。這張表沒有任何東西擋住違反這條規則的資料。要檢查它、之後再用它重新設計這張表，第一步是把這種規則寫成精確的形式。

從已知出發

先複習：superkey

t[K] 是 tuple t 在 attribute 集合 K 上的值。K 是 R 的 superkey，意思是在每個 legal instance（遵守現實規則的任何一份資料）裡，兩個不同的 tuple 在 K 上的值都不同。（superkey 頁）

把 superkey 換個方向說：兩個 tuple 只要在 K 上相同，就是同一個 tuple。relation 是集合，所以「同一個 tuple」就等於「在 R 的每個 attribute 上都相同」。

t₁[K] = t₂[K] ⇒ t₁[R] = t₂[R]

「同店同電話」也是這個形狀，只是右邊弱一點：兩列在 shop 上相同，只要求它們在 shop_phone 上相同，不要求整列相同（t₁ 和 t₃ 的 item 本來就該不同）。

所以只要把右邊的「整個 R」換成任意一組 attribute，就得到我們要的寫法。superkey 就是右邊剛好是整個 R 的特例。

正式定義

functional dependency

白話地說，functional dependency 是一條「只要左邊相同，右邊就一定相同」的規則。

設 R 是 relation schema，α ⊆ R、β ⊆ R。functional dependency（函數相依） α → β 是關於 R 的一條規則：任兩個 tuple 若在 α 上的值相同，在 β 上的值也必須相同。讀作「α 決定 β」；α 叫左邊，β 叫右邊。只有一個 attribute 時常省略大括號，寫成 shop → shop_phone。課本和考卷常縮寫為 FD；本站一律寫全名。

這條規則可以拿一份資料來檢查，也可以拿來描述所有合法資料。這兩件事要分開命名。

satisfy

一份 instance r(R) satisfy（滿足） α → β，是指 r 裡的每一對 tuple 都遵守這條規則：

對所有 t₁, t₂ ∈ r：t₁[α] = t₂[α] ⇒ t₁[β] = t₂[β]

只要找到一對 tuple 在 α 上相同、在 β 上不同，r 就不 satisfy 這條 functional dependency。

holds

α → β 在 R 上 holds（成立），是指 R 的每一個 legal instance （遵守現實規則的任何一份資料） 都 satisfy （每對 tuple 都遵守這條規則） 它。

satisfy 是一份 instance 的性質，直接看資料就能檢查。holds 是 schema 加上現實規則的性質，只能從規則判斷：不 satisfy 就一定不 hold，但 satisfy 了不代表 hold。

用這個語言重寫 superkey：K 是 R 的 superkey，若且唯若 K → R 在 R 上 holds。

例子

例 1：一個 attribute 決定一個 attribute

orders(order_no, shop, shop_phone, item)
order_noshopshop_phoneitem
t₁A001阿嬤豆花02-5550-0101花生豆花
t₂A002小林麵館02-5550-0202牛肉麵
t₃A003阿嬤豆花02-5550-0101芋圓豆花
t₄A004河堤咖哩02-5550-0303豬排咖哩

檢查 shop → shop_phone：只有 t₁ 和 t₃ 兩列的 shop 相同，它們的 shop_phone 也相同，所以這份 instance satisfy 它。其他店都只出現一次，沒有東西要比。

它在 orders 上也 holds，但理由是現實規則「一間店只有一個電話」，不是這四列資料。

例 2：左邊兩個 attribute，一對相鄰的 tuple 就能推翻

售票系統的規則是「同一個場館、同一個座位、同一天，只賣給一個人」。

ticket(venue, seat, show_date, holder)
venueseatshow_dateholder
t₁星光館A-1212/24周先生
t₂星光館A-1212/25鄭小姐
t₃河岸劇場A-1212/24林小姐
t₄星光館B-0312/24周先生

{venue, seat} → holder：t₁ 和 t₂ 兩列在 venue、seat 上都相同，holder 卻不同。一對就夠了：這份 instance 不 satisfy 它，所以它也不可能 hold。

{venue, seat, show_date} → holder：四列裡沒有任何兩列在這三個 attribute 上都相同，所以 satisfy。它 holds，理由是售票規則。

非例：右邊兩個 attribute，satisfy 了，卻不 hold

同一份 ticket instance，檢查 holder → {venue, show_date}。holder 重複的只有周先生的 t₁ 和 t₄，兩列都是（星光館, 12/24），所以這份 instance satisfy 它。

但現實裡沒有規則禁止周先生另外買一張 12/25 河岸劇場的票，加上那一列的 instance 也是 legal instance，而且不 satisfy 這條規則。不成立的條件是「每一個 legal instance 都 satisfy」，所以它不 hold。

例 3（邊界）：空的 instance 和只有一列的 instance

ticket(venue, seat, show_date, holder)
venueseatshow_dateholder
（沒有任何 tuple）

要推翻一條 functional dependency，需要一對在左邊相同、右邊不同的 tuple。空的 instance 和只有一列的 instance 都湊不出這樣一對，所以它們 satisfy 每一條 functional dependency，連 holder → seat 這種明顯不合理的也算。

這說明了為什麼檢查資料只能用來推翻：資料越少，被 satisfy 的規則就越多，但這些規則不見得 hold。

右邊是左邊子集的 functional dependency，例如 {venue, seat} → venue，在任何 instance 都自動 satisfy，有自己的名字：trivial functional dependency。

重點整理

問題 Problem
「同一間店只有一個電話」這種現實規則需要精確的寫法，才能檢查資料，之後再拿來重新設計 relation。
核心 Key idea
α → β：任兩個 tuple 在 α 上相同，就必須在 β 上相同；satisfy 看一份 instance，holds 看每一個 legal instance。
來自 Built from
superkey：兩個 tuple 在 K 上相同，就在整個 R 上相同。
差別 Difference
右邊不必是整個 R，可以是任何一組 attribute；superkey 只是 K → R 這個特例。

考試怎麼考

第一種題型給一份 instance，問它 satisfy 哪些 functional dependency。做法是對每條規則找「左邊相同、右邊不同」的一對 tuple。一般經驗

第二種題型給一組在 R 上 holds 的 functional dependency，接著問 superkey、拆表，或是否符合 BCNF（之後的正規化形式，規劃中頁面）。這一章後面的內容都以它為輸入。課程依據：Ch.7

最常錯的一步是看到 instance satisfy 某條規則，就寫「holds」。instance 只能推翻，不能證明。一般經驗

第二常錯的是把方向弄反：shop → shop_phone holds，不代表 shop_phone → shop 也 holds。一般經驗

自我檢測

停車場的進場紀錄，每一列代表一次停車。

parking(plate, slot, floor, entry_time)
plateslotfloorentry_time
t₁AAA-1001A01B108:10
t₂BBB-2002B07B208:25
t₃CCC-3003A01B109:40
t₄DDD-4004B12B210:05
  1. 這份 instance satisfy slot → floor 嗎？
  2. 這份 instance satisfy floor → slot 嗎？不 satisfy 的話，指出是哪一對 tuple。
  3. 這份 instance satisfy plate → slot。能不能因此說它在 parking 上 holds？
看答案
  1. satisfy。slot 相同的只有 t₁ 和 t₃（都是 A01），它們的 floor 都是 B1。
  2. 不 satisfy。t₂ 和 t₄ 的 floor 都是 B2，slot 卻是 B07 和 B12。（t₁ 和 t₃ 在 B1 上沒有問題，但一對反例就夠了。）
  3. 不能。四列的 plate 都不同，所以根本沒有一對要比，satisfy 是白來的。而且每一列是一次停車，同一台車改天再來停到別的格子完全合法，所以它在現實裡也不 hold。

最容易錯的是第 3 題：把「這份資料沒有反例」當成「規則成立」。避免的方法是先問「這條規則是現實規定的嗎？」，再看資料。第 2 題則要小心方向：第 1 題成立，不代表反過來也成立。
