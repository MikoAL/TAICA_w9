superkey（超鍵）

動機

一間健身房把會員存在一個 relation 裡：會員編號、姓名、電話、方案。櫃台要把「林雅婷」的方案改成年繳，於是寫「把姓名是林雅婷的那一列改掉」。

member(member_no, name, phone, plan)
member_nonamephoneplan
t₁M001林雅婷0912-000-101月繳
t₂M002陳柏翰0912-000-202年繳
t₃M003林雅婷0912-000-303季繳

結果 t₁ 和 t₃ 兩列都被改了：剛好有兩位會員都叫林雅婷。用姓名找人，就是在賭「不會有人同名」。

我們需要一組 attribute，保證看到它的值就只會對到一列。而且這個保證不能只對今天的資料成立：明天新加入的會員，也不能讓它失效。

從已知出發

先複習：relation

relation 是 tuple 的集合，每個 tuple 在每個 attribute 上有一個值。relation schema 是名字加上 attribute 清單，像 member(member_no, name, phone, plan)；instance 是某個時刻實際存著的那些 tuple。（relation 頁規劃中）

因為 relation 是集合，同一個 tuple 不會出現兩次。所以任兩個不同的 tuple，至少在一個 attribute 上不同：把全部 attribute 一起看，一定分得出任兩個 tuple。

這個「分辨能力」就是動機裡缺的東西。問題只剩下：能不能只看一部分 attribute，就保留這個能力？

為了講清楚「一部分」，先約定一個寫法：K 是一組 attribute，t[K] 表示 tuple t 在 K 裡那些 attribute 上的值。例如 t₁[{name, plan}] = (林雅婷, 月繳)。

對應關係是：全部 attribute 的集合 R 永遠有分辨能力；superkey 就是任何一個仍然保有這個能力的子集 K ⊆ R。

正式定義

legal instance

白話地說，legal instance 是「遵守所有現實規則的那些資料」：不只今天存著的這一份，而是規則允許出現的任何一份。

一個 legal instance（合法實例） 是滿足 R 所有現實世界限制的 instance r(R)。

superkey

設 R 是一個 relation schema，K ⊆ R。若對 R 的每一個 legal instance （遵守現實規則的任何一份資料） r，r 裡任兩個不同的 tuple 在 K 上的值都不同，就稱 K 是 R 的 superkey（超鍵）：

對每個 legal instance r：t₁, t₂ ∈ r 且 t₁ ≠ t₂ ⇒ t₁[K] ≠ t₂[K]

注意判斷的對象是 schema 加上現實規則，不是某一份 instance。一份 instance 只能證明 K 不是 superkey（找到兩個不同的 tuple 在 K 上相同），永遠不能證明 K 是 superkey。

例子

例 1：全部 attribute 一定是 superkey

在動機的 member 裡，K = {member_no, name, phone, plan} 是 superkey。理由跟資料無關：relation 是集合，兩個不同的 tuple 不可能在所有 attribute 上都相同。任何 relation schema 都至少有這一個 superkey。

例 2：一個 attribute 就夠，加了也還是

健身房的規則是「每位會員拿到一個不重複的會員編號」，所以 {member_no} 是 member 的 superkey。

{member_no, plan} 也是 superkey：兩個 tuple 若在 member_no 上已經不同，多看一個 plan 也還是不同。superkey 加上任何 attribute 仍然是 superkey，所以 superkey 不必是「最小」的。

例 3：每個 attribute 都會重複，要三個一起看

共享空間的會議室借用表，規則是「同一間會議室、同一天、同一個時段，只借給一個社團」。

booking(room, day, period, club)
roomdayperiodclub
t₁A11/20上午讀書會
t₂A11/20下午桌遊社
t₃B11/20上午讀書會
t₄A11/21上午吉他社

四個 attribute 各自都有重複的值。room、day、period 三個裡任取兩個，這份資料也已經刷掉了：t₁ 和 t₂ 在 {room, day} 上相同，t₁ 和 t₃ 在 {day, period} 上相同，不相鄰的 t₁ 和 t₄ 兩列在 {room, period} 上相同。

{room, day, period} 是 superkey，理由來自規則，不是來自這四列資料：規則禁止兩列在這三個 attribute 上都相同。

非例：這份 instance 裡沒有重複，{name} 卻不是 superkey

member(member_no, name, phone, plan)
member_nonamephoneplan
t₁M010張志明0912-000-404月繳
t₂M011吳佩珊0912-000-505年繳

兩列的 name 不同，所以這一份 instance 裡 name 能分辨每一列。但健身房沒有「不准同名」的規則，有兩位同名會員的 instance（像動機那份）也是 legal instance。不成立的條件是「對每一個 legal instance」。

例 4（邊界）：空的 instance，以及最多只有一列的 relation

member(member_no, name, phone, plan)
member_nonamephoneplan
（沒有任何 tuple）

空的 instance 裡找不到兩個不同的 tuple，所以任何 K，甚至空集合 ∅，都「沒有重複」。這正是定義要看每一個 legal instance 的原因：只看一份資料，什麼都證明不了。

反過來，有些 relation 依規則就最多只有一列，例如只存一組系統設定的 settings(site_name, max_members)。這時連 ∅ 都是 superkey：任兩個 tuple 在 ∅ 上的值一定相同（都是空的），而規則保證根本不會有兩個不同的 tuple。

重點整理

問題 Problem
更新或刪除資料時要能精確指出一個 tuple，而且以後新增的資料也不能讓這個方法失效。
核心 Key idea
superkey 是一組 attribute，在每個 legal instance 裡，不同的 tuple 在它上面的值都不同。
來自 Built from
relation 是 tuple 的集合，所以把全部 attribute 一起看，一定分得出任兩個 tuple。
差別 Difference
superkey 只用一部分 attribute 就保住這個分辨能力，而且必須對每個 legal instance 成立，不只眼前這一份。

考試怎麼考

最常見的題型是給一個 relation schema 和幾條現實規則，問哪些 attribute 集合是 superkey。superkey 也是 candidate key（最小的 superkey，規劃中頁面）和 primary key（規劃中頁面）的起點。課程依據：Ch.2

到了正規化，判斷 superkey 改用 functional dependency（「左邊相同，右邊就相同」的規則）和 attribute closure（從一組 attribute 推出它能決定的所有 attribute，規劃中頁面）。課程依據：Ch.7

最常錯的一步是看著題目給的 instance 說「這欄沒有重複，所以是 superkey」。instance 只能用來否定；肯定一定要回到規則。一般經驗

第二常錯的是以為 superkey 必須最小。最小的那種另有名字，叫 candidate key。一般經驗

自我檢測

共享單車的租借紀錄，每一列代表一次租借，start_time 精確到分鐘。規則：一台車在同一個時間點最多只會開始一次租借；很多台車可以在同一分鐘、從同一個站被借走。

rental(bike_id, station, start_time, card_no)
bike_idstationstart_timecard_no
t₁B17河濱站11/20 08:02C-3301
t₂B42車站前11/20 08:02C-5120
t₃B17公園站11/20 18:45C-3301
  1. {bike_id, start_time} 是 rental 的 superkey 嗎？
  2. 這份 instance 裡 station 三列都不同。{station} 是 superkey 嗎？
  3. {bike_id, start_time, station} 是 superkey 嗎？
看答案
  1. 是。規則保證同一台車不會在同一個時間點開始兩次租借，所以任何 legal instance 裡，兩個不同的 tuple 不可能在 bike_id 和 start_time 上都相同。
  2. 不是。規則明說很多台車可以從同一個站被借走，所以存在兩列 station 相同的 legal instance。這份 instance 剛好沒重複，不代表什麼。
  3. 是。它包含第 1 題的 superkey，superkey 加上任何 attribute 仍然是 superkey。

最容易錯的是第 2 題：被眼前的資料說服。避免的方法是每次都問「規則有沒有禁止兩列在 K 上相同？」，沒有禁止就不是 superkey。
